# Synctus 协议与加密设计

本文描述 Synctus 的线路协议与密码学设计，便于审查与重新实现。

## 1. 威胁模型

要防的：

- **中继服务器本身。** 服务器是不可信的转发节点。它看得到房间标识、设备标识、
  消息大小与时间，看不到任何状态内容。
- **网络中间人。** 客户端到服务器一段用 TLS，防止旁观者看到房间标识、
  重放或重排帧。
- **知道房间标识但不知道配对码的人。** 无法读取任何内容，也无法加入
  已有人在的房间。

不防的，以及原因：

- **对端设备本身。** 双方在同一个房间里共享一把密钥，彼此可以读写全部内容。
  这是"同步状态"这件事的前提，不是缺陷。督促功能更是明确建立在这一点上。
- **抢占空房间的拒绝服务。** 知道房间标识的人可以先进入一个空房间，
  把预期的认证响应设成错的，从而挡住真正的用户，直到房间清空。
  房间标识来自 80 位配对码的 HKDF 输出，猜中它才是难点；
  这是可用性问题，不是机密性问题。详见 §4。
- **元数据。** 服务器知道两台设备在什么时间通信、消息多大。
  隐藏这些需要填充与固定速率发送，代价与收益不匹配。
- **对方谎报数字。** 专注分钟数由本机的番茄钟产生，没有任何办法证明那段时间
  真的在工作。这个工具依赖的是两个人都想被督促，而不是密码学上的不可否认。

## 2. 密钥派生

一切都从一个共享的**配对码**派生，因此没有账号系统，服务器也不持有任何密钥。

```
配对码（规范化：仅保留字母数字并转大写）
  │
  │ Argon2id（m=64MiB, t=3, p=1, salt="synctus/room/v1"）
  ▼
32 字节房间根密钥
  │
  │ HKDF-SHA256
  ├─► room_id   16 字节 · info="synctus/v1/room-id" · 明文发给服务器
  ├─► auth_key  32 字节 · info="synctus/v1/auth"    · 证明房间成员身份
  └─► msg_key   32 字节 · info="synctus/v1/message" · XChaCha20-Poly1305 载荷密钥
```

**为什么 salt 是固定的。** 双方必须只凭配对码就派生出同一个密钥，
没有地方存放随机 salt。因此 Argon2id 在这里的作用是抬高弱配对码的暴破成本，
而不是防彩虹表。生成的配对码为 16 个字符、32 符号字母表，即 **80 位熵**，
本身已远超暴破可行范围。

**规范化。** `abcd-efgh` 与 `ABCD EFGH` 是同一个房间，用户手抄配对码时
不必在意分隔符与大小写。

## 3. 帧格式

长度前缀，一次写入一个完整帧：

```
┌────────────┬──────────┬──────────────────────┐
│ len: u32be │ kind: u8 │ body: len-1 字节     │
└────────────┴──────────┴──────────────────────┘
```

`len` 上限 64 KiB，先校验再分配，这是每条连接的内存上界。
`body` 是 JSON（除 `Ping`/`Pong` 无 body）。

| kind | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| 1 | `Hello` | C→S | 协议版本、房间标识、设备标识 |
| 2 | `Challenge` | S→C | 32 字节随机数 |
| 3 | `Auth` | C→S | 对随机数的 HMAC |
| 4 | `Welcome` | S→C | 服务器时间、已在房间内的设备、心跳间隔 |
| 5 | `Error` | S→C | 错误码与描述 |
| 6 | `Relay` | 双向 | **端到端加密**的对端载荷 |
| 7 | `Presence` | S→C | 某设备上线/下线 |
| 8 | `Ping` | 双向 | 保活 |
| 9 | `Pong` | 双向 | 心跳应答 |

## 4. 握手与房间准入

```
客户端 ──▶ Hello    { proto, room_id, device_id }
服务器 ──▶ Challenge{ nonce }                       ← 每个房间一个，房间存续期间不变
客户端 ──▶ Auth     { HMAC(auth_key, "synctus-auth" ‖ nonce) }
服务器 ──▶ Welcome  { server_time, peers, heartbeat_secs }   或 Error
   …随后双向收发 Relay / Presence / Ping
```

服务器不知道配对码，因此无法独立验证 HMAC。它的角色是**见证者**：

- 每个房间创建时生成一个随机 challenge，房间存续期间保持不变。
- **第一个**设备的回答被记录为该房间的预期值。
- 之后加入的设备必须给出**完全相同**的回答（常量时间比较）。

由此得到的性质与代价，如实列出：

- 知道房间标识但不知道配对码的人，无法加入已有人在的房间；
  即使能加入也读不到任何内容，因为载荷是端到端加密的。
- 知道房间标识的人**可以**先占住一个空房间并设下错误的预期值，
  把真正的用户挡在外面，直到房间清空。这是拒绝服务，不是信息泄露。
- 房间清空时房间对象被删除，challenge 随之轮换。
- 在房间持续有人期间，抓到的 MAC 可以被重放。客户端到服务器一段是 TLS，
  要抓到它需要已经在这一段的内部。

## 5. 载荷加密

`Relay` 帧的 `body` 是 base64 的 `nonce ‖ ciphertext`：

- **算法**：XChaCha20-Poly1305
- **nonce**：每条消息 24 字节随机数。192 位 nonce 下随机生成在本项目的
  消息量级上碰撞概率可忽略，无需维护计数器状态。
- **AAD**：发送方的 `device_id`。因此房间内的一台设备**无法**把别人的
  密文冒充成另一台设备发出的。
- 服务器另行用连接的已认证身份**覆写** `Relay.from`，所以伪造发送方
  在两层上都被挡住。

明文是一个 JSON 标签联合：

```jsonc
{"t": "status", "device_id": "…", "presence": "resting", "battery": {…},
 "focus_today_min": 75, "goal_min": 100, "streak_days": 3, …}
{"t": "nudge",  "kind": "nag", "text": "今天还差 25 分钟", "from_name": "…", "at": …}
{"t": "todos",  "device_id": "…", "items": [...], "at": …}
{"t": "ping",   "at": …}
```

## 6. 督促相关字段

`status` 里与督促直接相关的三个字段：

| 字段 | 含义 |
| --- | --- |
| `focus_today_min` | 今日累计专注分钟数。这才是能真正问责的数字，所以与回合数分开同步 |
| `goal_min` | 每日目标分钟数。同步它，对方的进度才有意义，而不是一个孤立数字 |
| `streak_days` | 连续达标天数，含今天（若今天已达标） |

它们跟随「同步番茄钟状态」这一个隐私开关，因为它们描述的是同一件事。

**摸鱼判定发生在接收端。** 发送方只上报前台应用名，是否算「摸鱼」由**接收方
自己的清单**决定。这样每个人定义自己在意什么，也避免了把一份"黑名单"当作
双方都同意的事实。

`nudge` 的 `nag` 类型允许穿透免打扰，但由**接收方**的
`allow_urgent_nudges` 决定是否真的穿透——催促的权力不能由发送方单方面主张。

## 7. 保留状态（retain）

`Status` 与 `Todos` 会被服务器按 `设备/槽位` 保留最新一条，新设备加入时回放。
这样后启动的一端立刻能看到对方，不必等下一个采样周期。

保留的是**密文**——服务器只是存着一段它读不懂的字节。
按设备加槽位分键，因此同一个人的电脑与手机不会互相覆盖。

`Nudge` 从不保留：迟到十分钟的"敲一敲"比没有更糟。

## 8. 时间与番茄钟

番茄钟只同步**截止时间戳**，不同步倒计时。因此：

- 每秒不需要发一条消息，对端本地插值即可。
- 休眠、进程挂起、Android doze 之后状态依然正确。

代价是依赖双方时钟大致一致。`Welcome` 带回服务器时间，
偏差超过 60 秒时客户端会给出警告，而不是默默算错。

## 9. 服务器侧的资源边界

| 机制 | 默认值 | 目的 |
| --- | --- | --- |
| 帧长上限 | 64 KiB | 每连接内存上界，分配前校验 |
| 房间数上限 | 10000 | 陌生人用随机房间号消耗内存的边界 |
| 每房间设备数 | 8 | 两人使用足够，留出多设备余量 |
| 转发限速 | 10/秒（突发 30） | 令牌桶，按连接独立 |
| 空闲超时 | 90 秒 | 回收僵死连接，需大于心跳 25 秒 |
| 握手超时 | 10 秒 | 连上不说话的连接不占用槽位 |
| 发送队列 | 每设备 64 帧 | 队列满即断开该设备，它会重连并取回保留状态 |

超过限速时服务器**丢弃该消息并回一条 `Error`，但不断开连接**：
突发通常是 bug 而不是攻击，断开会让用户的状态直接消失。

## 10. 重连

指数退避，起始 1 秒、上限 30 秒，并叠加最多 25% 抖动，
避免两端同时重启后以相同节奏反复冲击服务器。

配对码或协议版本错误属于**终态**：重试没有意义，
客户端停止重连并等待用户修改设置。

每次成功连接后立刻重发最后一次本地状态，
配合服务器的保留状态，双方在一个来回内完成互相可见。
